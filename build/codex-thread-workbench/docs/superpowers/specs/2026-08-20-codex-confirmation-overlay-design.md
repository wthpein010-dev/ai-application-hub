# Codex 待开工确认悬浮窗设计

**日期：** 2026-08-20  
**状态：** 已确认  
**适用项目：** CodexThreadWorkbench

## 目标

在现有 Codex 多会话工作台进程中增加一个独立悬浮窗，集中显示已经结束当前回合、并在最后回复中明确等待用户确认后开始实施的 Codex 任务。悬浮窗允许用户确认单个任务或一键确认全部任务，并把固定消息发送到每个对应的真实 Codex 任务。

固定确认消息为：

> 确认，继续开始做，完成前不要停。

## 非目标

- 不自动同意命令执行或文件修改等 `app-server` 原生安全审批。
- 不替代现有工作台主窗口中的审批交互。
- 不读取或保存 Codex 登录凭据、Token、Cookie 或完整聊天副本。
- 不扫描或自动启动超过 24 小时的历史任务。
- 不在工作台退出后额外常驻后台。

## 架构

功能作为现有 Avalonia 桌面应用内的第二个窗口实现，并与主工作台共享同一个 `ICodexThreadClient` 和 `codex app-server` 连接。

新增四个职责明确的组件：

1. `ConfirmationMonitor`：启动时补扫最近 24 小时的任务，运行期间定期读取线程摘要；只深读新增、更新时间变化或尚未评估的空闲任务。
2. `ConfirmationDetector`：从线程状态和最后消息中纯函数式判断是否为“等待开工确认”，并生成待确认候选。
3. `ConfirmationOverlayViewModel`：维护候选集合、发送进度、单条确认、全部确认、忽略和失败重试状态。
4. `ConfirmationOverlayWindow`：无边框、顶部居中、始终置顶、不抢键盘焦点、不出现在任务栏；无候选时隐藏，有候选时显示。

现有 `MainViewModel`、线程卡片和原生安全审批流程保持不变。应用启动器负责创建共享客户端、主窗口、悬浮窗和监控器；应用关闭时按确定顺序停止监控、关闭悬浮窗、保存工作区并释放客户端。

## 识别规则

候选任务必须同时满足：

1. 线程处于空闲状态，且最新回合为已完成状态；
2. 最后一条有效对话消息来自 Codex，之后没有新的用户消息；
3. 最后一条 Codex 回复同时包含“请求用户确认”和“确认后开始实施”两类强语义；
4. 启动补扫时，线程更新时间在最近 24 小时内；运行期间则评估监控器观察到的新完成回合；
5. 当前的 `线程 ID + 最后 Codex 消息 ID` 未被确认、忽略或正在处理。

第一版使用保守、可测试的确定性规则，不调用外部模型，也不要求 API Key。确认语义包括“请确认”“确认后”“回复确认”“是否按此方案”等；实施语义包括“开始开发”“开始实施”“进入实现”“开始制作”“继续执行”“按方案落地”等。只有两类语义同时命中才显示，普通任务完成、可选后续建议或一般提问不显示。

检测器输出包含线程 ID、标题、最后消息 ID、用于展示的确认请求摘要和更新时间。摘要只保存在内存中，不写入设置文件。

## 监控与数据流

1. 工作台连接 `app-server` 并完成初始化。
2. 监控器调用 `thread/list` 获取最近任务摘要。
3. 启动时过滤到最近 24 小时；后续只处理新增或 `updatedAt` 变化的空闲任务。
4. 对候选摘要调用 `thread/read`，投影最近对话和最新回合状态。
5. 检测器判断是否等待开工确认。
6. 视图模型按更新时间倒序更新候选集合。
7. 集合从空变为非空时显示悬浮窗；变为空时隐藏。

默认轮询间隔为 2 秒。监控器缓存每个任务最后评估的更新时间和最后消息 ID，避免反复深读未变化任务。一次轮询失败不会清空现有候选，下一轮自动重试。

依据 OpenAI 官方 `app-server` 文档，线程读取与继续对话分别使用线程历史接口以及 `thread/resume`、`turn/start` 链路：<https://learn.chatgpt.com/docs/app-server>。

## 悬浮窗交互

悬浮窗位于主屏幕工作区顶部居中，使用紧凑纵向列表。每条候选显示：

- 任务标题；
- 最后一条确认请求的单行或双行摘要；
- `确认继续` 按钮；
- `忽略` 按钮；
- 失败时的错误摘要和 `重试` 按钮。

点击任务标题时，通过应用支持的任务导航能力打开对应 Codex 任务；如果当前运行环境没有可调用的导航接口，则保持标题为展示文本，不尝试模拟鼠标操作。

窗口顶部显示待确认数量和 `一键全部确认`。批量确认按当前列表顺序逐条发送，并显示 `正在确认 i/n`。每个任务独立成功或失败：成功项立即移除，失败项保留，不回滚其他成功项。

为避免误操作，批量按钮只包含当前可见且未处于发送中的候选。批量执行期间禁用第二次批量触发，但不冻结错误信息展示。

## 发送流程

单条和批量确认共用一个发送服务：

1. 将候选标记为发送中；
2. 调用 `thread/resume` 恢复目标任务；
3. 调用 `turn/start` 发送固定确认消息；
4. 成功后记录本次 `线程 ID + 消息 ID` 已处理并从列表移除；
5. 失败时恢复可操作状态，保留候选并显示简短错误。

处理记录只需保存在当前进程内。即使程序在发送成功后立即退出，线程中的新用户消息也会使同一旧回复不再满足“最后消息来自 Codex”的检测条件，因此不会重复确认。

## 窗口生命周期

- 主窗口显示与悬浮窗显示相互独立。
- 主窗口最小化、失焦或被遮挡时，悬浮窗仍保持置顶。
- 悬浮窗显示时不主动抢占当前应用焦点。
- 主屏幕工作区尺寸变化时重新计算顶部居中位置。
- 无候选时使用真正的窗口隐藏，不保留透明点击层。
- 关闭主工作台会先停止监控，再关闭两个窗口并释放共享客户端。

## 错误与安全

- 连接暂时中断：保留现有候选，显示轻量离线状态，重连或下一轮读取成功后恢复。
- 某个任务已被其他客户端回复：发送前重新读取；若最后消息 ID 已变化，则直接移除旧候选，不发送。
- 某个任务已重新运行：发送前重新读取；若不再空闲，则移除或等待下一轮重新评估，不向进行中的回合追加固定确认消息。
- 批量部分失败：成功项保持成功，失败项可单独重试。
- 检测到疑似但不满足双语义门槛的任务：不显示，优先避免误启动。
- 原生命令/文件审批：继续由现有 `ApprovalRequested` 流程处理，绝不进入此悬浮窗。

## 测试策略

### 核心单元测试

- 等待确认的中英文典型表达能被识别。
- 只有确认词、只有实施词、普通完成消息和一般问题不会被识别。
- 最后消息为用户消息、最新回合未完成或线程仍运行时不会被识别。
- 24 小时边界、消息 ID 去重和忽略逻辑正确。
- 单条确认依次调用恢复与开始回合，并发送精确固定文本。
- 发送前状态或最后消息变化时不会误发。
- 批量确认的顺序、进度、部分失败和重试正确。

### 监控测试

- 启动补扫仅深读最近 24 小时的空闲任务。
- 未变化任务不会在每轮重复深读。
- 更新时间变化或新完成任务会重新评估。
- 暂时读取失败不会清空候选，取消令牌能确定性停止循环。

### 桌面与生命周期测试

- 候选从零变为一时显示窗口，从一变为零时隐藏。
- 窗口无边框、置顶、隐藏任务栏且定位在主屏幕顶部居中。
- 主窗口最小化不隐藏待确认悬浮窗。
- 关闭应用时监控停止、窗口关闭、客户端只释放一次。

### 回归与实机验收

- 运行 Debug 与 Release 全部 .NET 测试。
- 启动本机交付版，构造一个真实等待确认任务，验证悬浮窗自动出现。
- 验证单条确认和一键全部确认分别发送到正确任务。
- 验证无候选时窗口完全隐藏，其他应用置前时悬浮窗仍保持置顶且不抢输入焦点。
- 验证原有任务卡、普通发送、停止回合和安全审批行为无回归。
