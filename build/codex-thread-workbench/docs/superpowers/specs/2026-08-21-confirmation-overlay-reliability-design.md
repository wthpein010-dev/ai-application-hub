# Codex 待确认悬浮栏可靠性设计

**日期：** 2026-08-21  
**状态：** 已确认  
**适用项目：** CodexThreadWorkbench Windows 确认悬浮模式

## 目标

悬浮栏在工具运行期间始终可见，并持续扫描最近任务。点击“确认继续”或“一键全部确认”后，只有在对应 Codex 任务中读到固定用户消息时才把候选移除。

固定消息为：

> 确认，继续开始做，完成前不要停。

## 根因与发送架构

Codex 桌面端持有任务 writer 时，工作台独立启动的 app-server 会让 `thread/resume` 返回 `thread ... already has an active writer`。旧实现把 app-server 调用成功当作消息已发送，且没有回读核验，因此按钮可能看似完成但目标任务没有用户消息。

新发送链路保留快速 app-server 路径。仅当 JSON-RPC 明确返回 active-writer 冲突时，Windows 版通过 `codex://threads/{threadId}?prompt=...` 精确打开任务并预填固定消息，确认前台窗口属于 Codex 桌面应用后发送 Enter。两条路径随后都轮询本地会话日志尾部；只有候选 Codex 消息之后出现完全相同的用户消息才算成功。未验证、超时或窗口识别失败时保留候选并显示“重试”，不能误报成功。

桌面兜底会让 Codex 窗口短暂切到前台。输入提交前必须再次验证前台进程，禁止向其他应用发送按键。

## 常驻与扫描

悬浮窗口不再因候选为空而隐藏。空闲时显示“暂无待确认 · 常驻扫描”，有候选时显示数量和可用的一键确认按钮。

扫描仍以两秒为周期，并继续只重读新增或更新时间变化的最近任务。候选检测不再调用会返回完整超长历史的 `thread/read(includeTurns=true)`；改为每个任务最多读取本地 JSONL 会话文件尾部 4 MiB，提取最后消息与回合边界。读取保持有限并发并增量发布，单任务失败、列表失败和下一轮自恢复语义保持不变。

检测器补充“你确认……后”“确认这个结构后”等明确等待确认表达；纯完成报告继续排除。

## 验收标准

- active-writer 冲突会触发精确任务深链与一次 Enter 提交。
- 任一路径没有读到固定用户消息时，候选保留并显示可重试错误。
- 已验证消息只发送到候选对应的任务，成功后候选才移除。
- 空列表时悬浮栏仍可见，一键确认禁用。
- 超长任务不会把完整历史载入内存，多个任务仍会有限并发并增量显示。
- “你确认这个结构后，我再进入规格和开发发布。”能被识别，纯交付完成回复仍不显示。
