# GameSpec Relay 设计规格

## 1. 产品定位

GameSpec Relay 是面向游戏研发团队的“需求转交付”Agent。它把群聊、会议纪要和策划文档中的零散信息，转换成可以立即分工、开发和验收的交付包。

它不替代飞书任务、Jira 或 GitHub，而是解决这些系统之前最耗时的一步：从模糊讨论中识别真正的决定、未决问题、跨职能任务、依赖关系和可验证的完成标准。

核心承诺：将一次 30-60 分钟的需求整理与任务拆分，压缩成约 3 分钟的“导入、分析、校对、导出”流程。

## 2. 目标用户与核心场景

### 目标用户

- 中小型游戏团队的制作人、主策划和项目经理。
- 需要频繁把需求交给程序、美术、音频和 QA 的功能策划。
- 使用 Vibe Coding 快速开发游戏原型，但经常因上下文不足导致返工的个人开发者。

### 首版核心场景

用户粘贴一段关于“Boss 二阶段表现增强”的群聊，或导入 `.txt`、`.md`、`.json`、`.csv` 文本资料。GameSpec Relay 自动输出：

1. 已确认决定与范围边界。
2. 尚未确认、会阻塞开发的问题。
3. 按策划、客户端、服务端、美术、特效、音频和 QA 拆分的任务。
4. 每项任务的输入、产物、依赖和验收标准。
5. 功能级测试用例与风险清单。
6. 可直接交给 Codex 的实现上下文包，以及 Markdown、JSON、CSV 导出。

## 3. 差异化

普通会议摘要工具回答“聊了什么”；GameSpec Relay 回答“接下来谁做什么、做到什么程度才算完成，以及这次变更会影响哪里”。

游戏研发专用能力包括：

- 理解关卡、角色状态机、资源命名、Prefab、动画、特效、音频事件、配置表和多端性能等游戏语义。
- 自动将表现需求拆成策划规则、程序逻辑、美术资产、音频资产和 QA 用例。
- 将“更有压迫感”“手感再爽一点”等主观表述转换为可测指标，同时保留必须由人确认的主观决策。
- 对新旧需求进行版本比较，标记新增、变更、删除以及受影响的任务和验收项。
- 生成适合 Vibe Coding Agent 使用的上下文包，而不是只生成项目管理卡片。

## 4. MVP 范围

### 必须包含

- 内置可一键载入的完整游戏需求示例。
- 多来源输入：粘贴文本、拖拽或选择文本文件。
- 本地游戏领域分析引擎；无需账号或 API Key 即可完成演示和基础分析。
- 可选 OpenAI-compatible 模型配置，用于更复杂的自由文本分析；密钥只保存在本机桌面应用的用户数据目录，不进入导出文件、日志或仓库。
- 需求分析结果：决定、疑点、范围、角色任务、依赖、验收标准、测试用例、风险。
- 人工校对：编辑任务、确认或保留疑点、调整优先级和负责人角色。
- 需求版本对比与影响提示。
- 导出 Markdown、JSON、CSV，以及复制 Codex 任务包。
- 浏览器内本地历史；桌面端本地项目文件。
- 完整网页演示、Windows 便携版、macOS x64/arm64 包。
- AI Application Hub 卡片必须依次提供“演示 / 视频 / Wins下载 / Mac下载”。
- 约 3 分钟 H.264 教学视频，配简体中文字幕，任一时刻仅显示一行字幕。

### 明确不做

- 不在 MVP 中成为完整项目管理系统，不实现工时、甘特图、考勤或团队权限。
- 不未经确认直接向群聊发送消息、创建任务或修改 GitHub Issue。
- 不解析音视频原文件；用户可粘贴或导入转写稿。
- 不读取私有仓库代码来做完整变更影响分析；首版影响分析基于用户提供的需求和可选项目词汇表。
- 不承诺云端协作、账号系统或跨设备同步。

## 5. 用户体验与信息架构

应用采用三段式工作台，三分钟内可以完整演示。

### 5.1 收件箱

- 左侧显示来源列表和原始内容。
- 支持粘贴、导入文件、添加项目词汇表和载入示例。
- 顶部显示来源数、字符数和检测到的参与角色。
- 用户选择“生成交付包”后进入分析状态。

### 5.2 决策台

- 中间区域按“已确认决定 / 待确认问题 / 范围边界”展示 Agent 结论。
- 每个结论保留来源片段，用户可追溯为什么得到该结论。
- 待确认问题使用阻塞级别：必须确认、建议确认、可延后。
- 未确认的关键问题不会被 Agent 擅自补成事实。

### 5.3 交付台

- 右侧按职能泳道展示任务卡片。
- 任务卡包含目标、输入、产物、依赖、优先级、验收标准和来源证据。
- 单击任务可编辑；依赖缺失或循环依赖时显式报错。
- QA 区自动汇总功能、边界、恢复、兼容和性能测试。
- 导出前提供“交付健康度”：范围完整度、可验收度、未决阻塞和依赖风险。

### 5.4 版本对比

- 保存当前分析为 V1，再导入变更讨论生成 V2。
- 展示新增、修改、删除的决定、任务和验收标准。
- 给出受影响职能和需要重新验证的测试用例。

## 6. 分析模型与数据结构

核心数据结构为 `DeliveryPack`：

```text
DeliveryPack
├─ project: 名称、版本、生成时间、来源摘要
├─ decisions[]: 结论、置信度、来源证据
├─ questions[]: 问题、阻塞级别、建议负责人、状态
├─ scope: inScope[] / outOfScope[]
├─ tasks[]
│  ├─ id / role / title / objective
│  ├─ inputs[] / outputs[] / dependencies[]
│  ├─ acceptanceCriteria[] / evidence[]
│  └─ priority / status / risk
├─ tests[]: 类型、前置条件、步骤、预期结果、关联任务
├─ risks[]: 风险、概率、影响、缓解方式
└─ health: 完整度、可验收度、阻塞数、依赖风险
```

本地分析引擎采用可解释的多阶段流水线：

1. 清理文本并识别说话人、时间和来源。
2. 按决定、建议、疑问、否定和约束切分语句。
3. 使用游戏领域词典将内容映射到职能和资产类型。
4. 通过任务模板生成最小可交付任务，并绑定原文证据。
5. 从需求中的时间、数值、触发条件和否定约束生成验收标准。
6. 根据状态变化、异常流程、设备限制和资源依赖生成测试与风险。
7. 运行一致性检查，识别无验收任务、悬空依赖、循环依赖和被当作事实的未决问题。

可选模型适配器只能生成同一 `DeliveryPack` 结构；所有模型结果仍通过本地验证器和人工校对门禁。

## 7. 技术架构

### 共享 Web 核心

- 原生 HTML、CSS、JavaScript，避免构建工具成为公开演示的运行依赖。
- UI、领域分析器、验证器、版本比较器和导出器均为可独立测试的 ES Modules。
- IndexedDB 或 localStorage 保存浏览器演示历史；不上传用户内容。

### Electron 桌面端

- 复用同一 Web 核心。
- 主进程仅负责原生文件选择、项目保存、导出和可选模型请求。
- `contextIsolation: true`、`nodeIntegration: false`，通过最小化 preload API 暴露能力。
- Windows 产出便携版；macOS 产出 x64 和 arm64 `.app` ZIP。
- 未签名包在下载页明确说明系统安全提示和打开方式，不伪装为已签名应用。

### 发布与下载

- 网页演示和视频页进入 `wthpein010-dev/ai-application-hub`。
- 桌面大包通过 GitHub Release 提供，避免把二进制大包直接塞入 Pages 仓库。
- GitHub Actions 分别在 Windows 和 macOS runner 上构建、执行 smoke test、记录架构和哈希，再发布 Release 资产。

## 8. 错误处理与安全

- 空输入、超大文件、无法解码的文件和不支持的格式均提供具体提示，不丢失已输入内容。
- 分析可取消；失败时保留来源和上一次成功的交付包。
- 循环依赖、缺少验收标准、重复任务和未解决的强阻塞问题会阻止“标记为可交付”，但不阻止草稿导出。
- 模型请求失败自动回退到本地分析器，并标记结果来源，不伪称模型已成功运行。
- 不在控制台、错误报告、导出文件、视频或演示数据中输出 API Key。
- 创建飞书任务或 GitHub Issue 属于外部写操作；MVP 仅生成预览或导出文件，不自动提交。

## 9. 视觉方向

视觉采用“制作人控制台”风格：深色工作台、青绿色状态色、橙色阻塞提示、清晰的职能泳道。页面重点是信息流与可追溯性，不使用与任务无关的装饰性按钮。

桌面主布局为三列：来源、决策、交付；移动端改为四步向导，避免横向溢出。所有状态不仅依赖颜色，还配合图标和文字。

## 10. 教学视频脚本目标

视频约 165-180 秒，覆盖：

1. 15 秒：混乱群聊造成返工的痛点。
2. 25 秒：载入 Boss 二阶段示例和项目词汇表。
3. 35 秒：Agent 提取决定、疑点和范围。
4. 45 秒：跨策划、程序、美术、音频、QA 拆任务及依赖。
5. 30 秒：补充确认项、查看健康度和测试用例。
6. 25 秒：生成 V2 并查看变更影响。
7. 15 秒：导出 Markdown/JSON/CSV 和 Codex 上下文包。

字幕每次只显示一行，视频分辨率为 1280×720，H.264 编码，总时长不得超过 4 分钟。

## 11. 验收标准

### 功能

- 内置示例从导入到生成交付包可以在无网络、无 API Key 的情况下完整运行。
- 示例至少生成 5 个职能任务、8 条验收标准、5 个测试用例和 2 个明确待确认问题。
- 每个决定、问题和任务至少关联一条来源证据。
- 用户编辑与确认状态在刷新后仍保留。
- V1/V2 对比能正确显示新增、修改、删除和受影响测试。
- Markdown、JSON、CSV 和 Codex 包可以下载或复制，内容与当前编辑状态一致。

### 质量

- 核心分析器、验证器、版本比较器和导出器具有自动测试。
- 桌面与 390×844 移动端无横向溢出，无控制台错误和资源加载错误。
- Windows 包完成解压、启动、分析、导出和退出测试。
- macOS x64/arm64 包由 macOS CI 构建；至少一个架构完成真实启动 smoke test，两个包均完成结构和架构验证。
- 视频可在真实浏览器点击播放，字幕可启用，媒体 Range 请求有效。

### 发布

- 新卡片位于 Hub“应用项目集合”末尾且仅出现一次。
- 四个按钮顺序严格为“演示 / 视频 / Wins下载 / Mac下载”。
- GitHub Pages 部署成功，主页、演示页、视频页、字幕、封面和下载链接均可从公网访问。
- 最终报告包含远端提交 SHA、Pages 工作流结果、公开 URL、视频时长、包体大小和 SHA-256、平台运行证据。

## 12. 成功判断

比赛演示中，观众应在前 30 秒理解：输入一段游戏团队讨论，GameSpec Relay 会生成可直接开工和验收的跨职能交付包。产品价值以“减少需求整理和返工”衡量，而不是以摘要字数或生成速度作为唯一指标。
