# Paws 关卡请求竞态保护设计

**日期：** 2026-07-22
**状态：** 已确认（用户要求持续直接优化，不中断询问）

## 目标

保证关卡库刷新与关卡打开遵循“最后一次请求生效”。用户快速连续点击 A、B 两关时，即使 A 的读取更慢、最后才返回，也不得覆盖已经打开的 B；连续刷新目录时，旧目录响应或旧错误也不得覆盖新目录状态。

## 根因

`WorkbenchController.openLevel()` 和 `refreshLevels()` 在每个 `await` 之后都会无条件提交结果。浏览器、localStorage、旧 AI 自动迁移和网络缓存都可能改变一次操作的耗时，因此完成顺序不等于用户意图顺序。当前没有 AbortSignal 或请求代次，慢旧响应会提交文档、目录、提示、连接状态和渲染器。

## 方案

在控制器维护两个单调递增代次：

- `openLevelEpoch`：每次真正开始打开关卡时递增。
- `refreshLevelsEpoch`：每次开始刷新目录时递增。

方法捕获自己的代次，并在每个异步边界后、任何状态提交前检查是否仍是当前代次。过期操作静默结束：不修改文档/目录、不渲染、不显示成功或错误提示、不触发损坏记录恢复。新请求失败时也不会让更旧的请求“复活”，因为旧代次已经永久失效。

确认对话框取消不算一次新操作，因此不会无故废弃当前仍在进行的打开请求。损坏记录恢复的递归打开会创建新代次；恢复前后的旧操作检查仍保留。

## 测试

使用真实 `WorkbenchController` 和可控 deferred API，不靠源码正则：

1. 同时打开 slow-A 与 fast-B，先完成 B 再完成 A；最终文档必须是 B，且 A 不得再触发渲染或成功提示。
2. 同时刷新 old 与 new，先完成 new 再完成 old；最终目录和默认文件必须来自 new。
3. 旧刷新最后抛错时，不得把已经在线的新目录改成错误状态。
4. 正常单次打开、损坏记录恢复和默认关自动打开的既有流程继续通过。
