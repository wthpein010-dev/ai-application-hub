# 《灯塔救援队》生效事件追加日志规格

状态：2026-10-04，按用户已确认的“持续优化至完整版并发布”授权实施。当前正式抖音 SDK 仍缺，故以模拟消息和 SDK 无关的直播队列验证。

## 目标与证据边界

1. 高弹幕量下，阶段内每条生效事件不再复制不断增长的观众、投票、去重和冷却历史，也不再重写整个检查点。
2. 生效事件在画面反馈和未来履约 ACK 之前，以可校验的追加记录落盘；崩溃恢复从最近完整检查点顺序重放，保留重复消息、投票和冷却语义。阶段切换、开局、暂停、恢复、结束及主动重置仍写完整检查点。
3. 公网 Windows 与 WebGL 模拟版玩法、美术、音效、镜头和控制不变。没有官方 SDK、玩法权限、真实直播间和审核时，仍明确标记本地模拟。

## 方案取舍

- 继续每条事件写完整检查点最简单，但观众数越多，复制和写入成本越高。
- 延迟批量保存可降低开销，却可能在已反馈或已 ACK 后丢失事件，不符合恢复目标。
- 采用阶段完整检查点 + 小型追加日志。每条被规则接受的普通事件记录事件原文、规则时钟、单调序号和 SHA-256 校验；恢复时只重放比检查点序号新的记录。日志达到 2 MiB 后做一次完整压缩。此方案既保留崩溃恢复路径，也把完整历史复制从“每条消息”降到阶段边界或压缩时。

## 持久化协议

- `RescueSnapshot.JournalSequence` 为可选的非负字段。旧 1.4.4 存档缺字段时按 0 读取，规则版本保持 1；轻量画面快照不能写盘。
- `CheckpointStore.AppendAccepted(GameEvent, RescueGame)` 仅接收本局普通事件；调用方先确认规则返回 `Accepted`，随后立即追加并 `Flush(true)`，之后才能显示生效反馈并向直播适配器交回生效回执。主线程同步写入，未引入后台乱序。
- 每行是 UTF-8 JSON，含日志格式版本、房间、本局、序号、应用时的规则时钟、事件字段和校验。单条上限 16 KiB；旧局残留和检查点序号以内的记录跳过，不合法记录、当前局乱序序号或重放未获 `Accepted` 时，恢复停在最后完整有效记录。撕裂尾部在恢复时截断，避免下次追加被旧残片挡住。
- 完整检查点保存当前已落盘序号。原子替换成功后才尝试清理旧日志；若崩溃发生在替换后、清理前，恢复按序号跳过旧记录，不重复应用。若日志清理失败，保留文件并在下次读取中跳过过期记录。
- 当日志超过 2 MiB，当前事件已经追加成功后写完整检查点并清理日志。压缩失败应保持已有日志可恢复，不可将未持久化事件报告为已保存。
- 恢复按记录时钟推进规则，再应用原事件；默认计时恢复精度保持原检查点语义，即恢复到最后生效事件或阶段边界，而不是模拟崩溃期间真实经过的时间。
- Windows 本地文件写入由 `Flush(true)` 完成；WebGL 的 IDBFS 文件更改由 Unity 模板异步同步到 IndexedDB。WebGL 页面在同步完成前被强制关闭，最近事件仍可能丢失；因此 WebGL 仅验证模拟试玩的刷新恢复，不将其当作未来正式直播的履约 ACK 持久性保证。

## 验收

- 测试先红后绿：旧存档兼容；200 条生效消息不产生 200 次完整快照；恢复后重复事件、同人投票和修理冷却仍生效；跨阶段压缩与崩溃后遗留旧日志不重放；撕裂或篡改尾部只损失该尾部；新局不吸收旧局事件；静音、镜头和操作保持既有测试结果。
- Unity EditMode 全量灯塔测试、定向 Node、Windows 全新解压短路和长路、桌面与 390px WebGL 完整一局，以及公网视频/下载/Pages/远端 CI 均需通过后才发布版本。
- 真实 SDK 流量、履约 ACK 和抖音正式玩法审核仍需获授权环境验证；本版不声称这些已经完成。
