# 馕饼拍拍响应用区发布设计

## 背景与根因

`馕饼拍拍响` 的 WebGL 成品、介绍视频和 Hub 卡片已经存在于远端 `main`，但卡片仍使用旧名称“馕了个馕”、`status: "game"`，演示页与视频页返回链接也指向 `#games`。Hub 会把 `game` 状态渲染到小游戏集合；同时 `loadApps()` 会优先读取浏览器已有的本地卡片数据，因此只修改默认卡片不足以让老用户看到新的应用区位置。

## 已确认目标

- 公开主页使用 `https://wthpein010-dev.github.io/ai-application-hub/index.html#apps`。
- 主页卡片名称统一为“馕饼拍拍响”。
- 卡片放在应用项目集合末尾，不出现在小游戏体验集合。
- 卡片只提供“演示”和“视频”两个入口，不提供源码、Unity 工程、微信包或下载按钮。
- 复用现有 Hub 内托管的 WebGL 成品和约 24 秒 H.264 介绍视频，不重复上传或重编码已经满足要求的媒体。
- 演示页和视频页的“返回主页”统一返回 `#apps`。

## 卡片与缓存迁移

卡片继续使用 `id: "nang-keng-pai-pai-xiang"`，保持现有入口 URL 不变。默认字段调整为：

- `name: "馕饼拍拍响"`
- `category: "Unity WebGL 休闲体验"`
- `status: "content"`，使其进入应用集合
- `badge: "休闲体验"`，避免界面展示内部分类标签“内容工具”
- `platforms.web` 指向现有演示页；Windows 与 Mac 入口保持空值
- `video` 指向现有视频页

`normalizeApp()` 对该固定 ID 执行项目级迁移：无论浏览器中保存的是旧默认卡片还是新默认卡片，都强制同步名称、分类、状态、徽标、入口、视频及无下载平台配置。这样旧 localStorage 不会继续把项目留在 `#games`，也不会产生下载按钮。

## 页面与资源

现有 `projects/nang-keng-pai-pai-xiang/` 目录继续承载 WebGL。只修改两个页面中的主页返回锚点和公开名称：

- 演示页返回 `../../index.html#apps`，页面标题和可访问名称使用“馕饼拍拍响”。
- 视频页返回 `../../../index.html#apps`，标题、说明和播放器可访问名称使用“馕饼拍拍响”。
- WebGL 加载、自解压逻辑、竖屏画布、游戏内容与视频媒体文件保持不变。

## 测试与发布门禁

先修改 `tests/nang-hub-catalog.test.mjs`，让旧实现按预期失败，再实现最小改动。测试必须证明：

- 卡片名称、分类、状态、徽标和入口正确。
- 卡片只产生“演示”和“视频”，没有 Windows、Mac 或 package 下载入口。
- 旧 localStorage 卡片会迁移到应用区配置。
- 演示页和视频页返回 `#apps`，且不再包含 `#games`。
- WebGL Gzip 自解压资源与视频文件仍存在且非空。

发布前运行相关 Node 测试、完整可运行测试集合、媒体探测和 `git diff --check`。推送 Hub `main` 后等待 GitHub Pages 成功，再在桌面端与 390×844 移动端验收：应用区能找到唯一卡片、按钮顺序为“演示/视频”、演示可加载、视频可点击播放、无横向溢出、控制台及请求无错误。

## 失败处理

- 若远端 `main` 在发布前前进，先拉取并仅做快进或正常变基，不强推。
- 若测试、媒体探测、Pages 工作流或公网验收失败，不宣称发布完成。
- 不修改或清理旧克隆中的未提交文件，不公开源码和下载包。
