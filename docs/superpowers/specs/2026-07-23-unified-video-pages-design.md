# Unified Video Pages Design

## Goal

Make every video destination opened from the AI Application Hub use one responsive player size, one visual language, and one return-home action. The return action always opens the top of the Hub home page.

## Chosen Architecture

Create one static Hub player contract in root-level assets:

- `assets/hub-video-player.css` owns the layout, colors, button dimensions, responsive behavior, and accessible focus treatment.
- `assets/hub-video-player.js` owns deferred source loading, playback start, video-error feedback, and optional chapter seek behavior.
- Each existing project video HTML remains an independent, directly openable page. It references the shared assets with its own relative path and supplies project-specific title, summary, media source, optional poster, optional caption track, and relative home URL.

This avoids a runtime dependency on a server, keeps copied folders usable on Windows and macOS, and prevents one project page from loading another project's media.

## Shared Page Contract

Every video page will provide these stable elements:

1. A fixed top-left anchor with class `hub-video-home`, visible at all viewport sizes, labeled "Return Home" (rendered as a Chinese numeric entity in HTML), and linked to the relative Hub `index.html` without a hash.
2. A single centered `main.hub-video-page` container.
3. Project-specific `h1` and one concise description.
4. One `section.hub-video-player` containing `video[data-src]`, `preload="none"`, `playsinline`, controls, and an explicit `#loadVideo` button.
5. A `div.hub-video-stage` with `aspect-ratio: 16 / 9`, `max-width: 960px`, and a black media surface. Landscape clips fill the stage; portrait clips remain contained and letterboxed without changing the stage dimensions.
6. Optional captions and chapters keep their existing project-specific content but use the shared styling.

The CSS will use neutral dark charcoal, off-white text, teal action color, 8px radii, and no decorative gradients. It will reserve room below the fixed home action so headings never sit underneath it. At mobile widths, the stage remains 16:9, page padding tightens, and no component creates horizontal overflow.

## Data and Navigation Flow

1. A Hub card opens its current project-specific video page.
2. The page renders instantly without assigning `video.src`.
3. The visitor selects the load-and-play action or a chapter.
4. Shared JavaScript assigns the existing `data-src` value, hides the overlay, loads the media, then requests playback.
5. A failed load replaces the overlay text with a clear retry message and leaves the browser controls available.
6. Selecting the Return Home action resolves the page-specific relative path and opens the top of `index.html`.

## Error Handling

- Missing `data-src` produces visible guidance instead of a blank player.
- A media `error` event restores an actionable overlay with a retry button.
- Playback rejection, such as browser autoplay restrictions, keeps the loaded controls visible and does not report a false success.
- Pages with no caption track remain valid; pages with a track preserve `kind="captions"`, Chinese language metadata, and default selection.

## Compatibility

The player uses static HTML, CSS, and standard HTML5 video APIs supported by current Chrome, Edge, Safari, and Firefox on Windows and macOS. It does not require a desktop application or platform-specific package. Existing H.264 MP4 assets remain untouched.

## Verification

Automated checks will extend video coverage to assert that each card video path exists and follows the shared contract: fixed home action, home URL resolving to Hub root, one 16:9 stage, lazy source, and an explicit load button.

Browser verification will cover all 22 paths for layout and console errors, plus representative landscape and portrait videos for actual load/play behavior at desktop and mobile viewports. The public GitHub Pages URLs will be retested after deployment.
