# 《灯塔救援队》Unity 直播互动游戏设计规格

日期：2026-09-29
状态：设计已获用户确认，2026-09-29；用户要求后续流程直接完成、不再逐步询问。本规格不表示已取得抖音玩法权限。

## 目标与证据

制作一款主播可以连续主持、观众能免费改变结果的 9:16 Unity 直播合作游戏。Windows 客户端供直播采集与官方事件接入，WebGL 版本供 GitHub Pages 公开试玩。首屏的观看目标是让陌生观众在 20 秒内理解“上船、选路、救人”。

飞书报告中《灯塔救援队》的 22/25 是内部策划初筛，并非市场转化、收入或留存数据。历史竞品只支持“低门槛输入能影响直播局势”这一机制参考，原创玩法的效果须通过试玩和真实试播验证。

## 一局体验

首版默认局长：集结 20 秒、选路 20 秒、短路每段 35 秒或长路每段 40 秒、冲刺与结算 40 秒，共 185 秒或 200 秒。每局目标是抵达灯塔、救起 3 名待救人员，避免船体归零。救起 3 人为完整成功，救起 1–2 人为部分成功，救起 0 人或船体归零为失败；结算同时展示剩余船体与用时，任何结局都能引出下一局。时长和难度数据可在开发调试中调整，但已开局的配置必须冻结。

| 阶段 | 默认时长 | 免费观众动作 | 主播动作 | 主要画面反馈 |
| --- | ---: | --- | --- | --- |
| 集结 | 20 秒 | 评论“上船”加入本局 | 简述目标与指令，点击开始 | 船员头像/昵称、船只离港、待救 3 人 |
| 选路 | 20 秒 | 评论“左”或“右”，每位观众一票 | 解释两路可见风险；平票时使用船长裁定 | 地图分叉、风险图标、实时票数 |
| 穿越障碍 | 3 段，短路各 35 秒／长路各 40 秒 | 根据当段险情评论“修理”或“照明”；点赞累积公共照明 | 播报受损与缺口，提醒免费贡献 | 船体、光束、障碍、救援进度、有效指令短反馈 |
| 冲刺与结算 | 40 秒 | 看救援结果、准备下一局 | 宣布结果、复盘关键选择 | 救起人数、全体贡献、结局插画、下一局提示 |

三段穿越各对应一个待救者。每段结束时，照明达到目标且船体未归零就救起该人；修理决定船体能否承受下一段风暴。冲刺是抵达灯塔和公布本局结果，不凭空再增加待救人数。

路线不做隐藏概率：短路的礁石更密、每段修理需求更高，但穿越时间较短；长路的迷雾更重、每段照明需求更高，穿越时间较长。阶段开始前显示两项需求和危险，观众可据此选择。每段险情由局种子和路线决定，画面预告风险；参与者可以从状态条看见自己的贡献。规则数据中的时长、船体伤害和目标值允许调参，但一局开始后锁定，不随付费或人数偷偷改变。

每段给修理与照明各一格可见的“系统值守”基础进度，保证冷场时仍会推进并结算；观众的免费指令补足进度并影响救援结果。系统帮助始终明示，不计入个人贡献。礼物只触发灯塔烟花、船旗等外观表现，不决定投票、船体、救援或排名。

### 首版可调数值

这些是实现与内测的初值，不是经市场验证的平衡结论。

| 参数 | 短路（左） | 长路（右） |
| --- | ---: | ---: |
| 每段时长 | 35 秒 | 40 秒 |
| 每段修理目标 | 4 格 | 3 格 |
| 每段照明目标 | 3 格 | 4 格 |
| 每段基础船体伤害 | 8 | 6 |

船体起始 100。每段开始修理和照明各有 1 格明示的系统值守；每条有效“修理／照明”评论加对应进度 1 格。同一用户同类指令相隔至少 3 秒才有效，每段每类最多计 4 次。每累计 20 次有效点赞，公共照明增加 1 格，每段最多 2 格。阶段结束先结算船体伤害：基础伤害加上未达修理目标的每格 12 点；再判断船体是否大于 0，且照明达到目标时救起本段待救者。船体归零立即失败，不进入后续阶段。进度上限显示为目标格，超出的有效评论只呈现感谢反馈，不再改变数值。礼物不改变任何上述参数。

## 规则与事件

规则内核是独立于 Unity 画面的单局状态机。它只接收标准化事件（来源、房间、局次、事件 ID、用户 ID、事件时间、指令、载荷），输出规则状态与视觉事件。模拟输入和正式直播适配器调用同一接口，使无平台权限时仍能完整试玩与验证。

- 入队：同一用户在本局只有一个船员身份，重复“上船”不增加人数。
- 投票：有稳定用户标识时，同一用户在一个窗口只计第一张有效票；无稳定标识时不伪造“每人一票”，改用平台可核验的聚合能力或调整规则。
- 修理、照明：只在对应阶段及任务窗口生效，按用户短冷却和单窗上限计入；过量评论不会无限堆数值。
- 点赞：只增加公共照明，不绑定个人排行；具体速率和上限须通过官方消息语义与试播调参。
- 礼物：单独处理履约与视觉反馈，任何延迟、重复或异常都不影响免费通关。
- 去重：事件 ID 与局次双重校验；迟到、重复、上一局消息记日志但不重复结算。多路推送只能有一个规则权威。

未投票时走屏幕标明的默认长路；平票由主播在倒计时内选择，主播未操作也走默认长路。观众可在任意进行中的阶段免费入队，但只在开放的任务窗口贡献；过期指令不会自动挪到下一阶段。对乱序消息按接收时所属阶段判断，不能用历史事件时间回写已结算阶段。有效事件每次只改变一个规则状态，并记录结果码供主播诊断。

状态机按 `等待开局 → 集结 → 选路 → 关卡 1/2/3 → 冲刺 → 结算` 单向推进，任何阶段都可进入 `暂停`，恢复时回到原阶段并延续剩余倒计时。每次阶段变更和有效输入后写入原子检查点，包含规则版本、房间、局次、种子、当前阶段、剩余时间、船体、进度、已救人数和去重记录。启动时只恢复同一房间且规则版本兼容的未结算局；否则提示重开。SDK 适配器需把点赞数量增量规范化为非负整数，礼物事件独立履约。若官方事件缺少足以稳定去重的标识，则正式直播模式不得启用，需针对实际 SDK 字段设计并验证替代键。

技术路径有两种可行选择：

| 选择 | 优点 | 代价与风险 | 建议 |
| --- | --- | --- | --- |
| Unity 客户端持有单局权威，官方 SDK 直推 | 单局规则与画面同进程，首轮试播部署简单、反馈延迟低 | 异常退出依赖本地检查点；跨主播统计与远端结算能力有限 | 首版推荐；先验证免费合作玩法与真实事件稳定性 |
| 官方 SDK 与 HTTPS 服务端双推，服务端权威裁决 | 便于跨端状态、统计与持续运营 | 增加 HTTPS 回调、验签、运维、两路消息对账；不能两路累加 | 真实联调证明需要时加入，或用户明确要求首版具备 |

已选首版由 Unity 客户端持有单局权威，并接入官方 Unity SDK 客户端直推，做好事件去重、ACK、掉线暂停和本地检查点。模拟适配器与 SDK 适配器放在规则内核之外；WebGL 不编译仅限 Windows 的 SDK 依赖。若实际联调证明需要双推，再另行扩展为服务端统一裁决，客户端只做低延迟表现。SDK 集成和真实直播验收以取得的 SDK 版本、开发者资质和账号权限为前提；没有包或权限时必须保留真实接口边界与诊断，不得伪造已接通状态。

## 画面与声音

画面为俯视 2D 卡通海图，主色为深海蓝、雾青和暖金灯光。船、岛礁、航迹用统一描边与柔和阴影；天气由平静海面渐变为风雨，再到灯塔破雾。上部显示当前目标和倒计时，中部保留船、路线与障碍的主舞台，下部显示“上船 / 左右 / 修理 / 照明”指令及船体、光照状态。昵称只短暂出现且限量排队，避免遮挡玩法。高频互动以小图标和光效合并显示，保留主播解说空间。

船只、岛礁、UI 和按钮音效以 Kenney Pirate Pack、UI Pack - Adventure、Interface Sounds 的 CC0 官方资源为候选。实际导入前逐包核对许可、文件、分辨率并记录来源；灯塔、风暴、待救人员和关键结局画面用原创同风格资源补齐。音效分为风浪环境、险情提示、修复、救援、结算五类；直播采集时允许主播一键关闭游戏声音或特效。

## 主播与试玩操作

主播面板提供开始、暂停、结束、静音特效、测试重置五项。可在开播前用模拟事件脚本完成一整局，屏幕上持续明确标注“演示模式”；只有官方 SDK 授权与真实直播间测试通过，才显示“直播已连接”。直播连接丢失时暂停倒计时，展示可解释的等待提示，并从最近的本地检查点恢复；恢复后跳过断线期间失效的阶段指令，不静默补结算。异常退出后提示恢复或重开，不静默结算。公开 WebGL 版让单人选择路、点击模拟互动、观看三种结局；清楚标注它是同规则的本地试玩。

## 交付与验收

Unity 工程保留可编辑场景、规则数据、美术来源清单和许可记录。生成 Windows x64 可运行包、WebGL 公开试玩、主播一页口播卡、游戏规则页和不超过 4 分钟的带单行字幕演示视频。Hub 的小游戏集合新增卡片，提供演示、视频和真实 Windows 包入口；不放空的 Mac 按钮。公开试玩与 Windows 包均须来自同一套规则版本。

验收分层：

1. 规则：固定种子下可重现胜负；重复、乱序、过期、限频和断线事件不会重复得分或结算；零礼物可以通关。
2. 可玩：一局可从集结到结算并重开；低参与和高参与都不死锁；主播能够在采集画面中清楚读取目标、指令与状态。
3. 平台：取得资质后，按官方流程验证评论、点赞、礼物、ACK、真实直播连接、掉线恢复与提审要求。未取得权限前只报告模拟版本已验证，不宣称抖音正式接入完成。
4. 发布：Windows 包实际启动并完成一局；WebGL 在桌面与手机浏览器可操作；视频公网实播；GitHub `main`、Pages 与 Hub 卡片所指资源逐项核验。

规则验收至少覆盖无观众、单人参与、多人刷屏三种模拟局，以及短路/长路、平票/无人投票、三种结局、断线重连和异常退出恢复。桌面与手机 WebGL 的操作、字号和帧率分别实测；不能用编辑器运行结果代替公开包验收。

试玩门槛采用报告建议作为待检验假设：10 名陌生观众中至少 8 名在 20 秒内说出目标、免费指令和胜利条件；之后至少 3 位不同风格主播各做 2 场完整试播，记录免费参与、重复参与、局间流失、主播停顿与异常。若免费互动不能改变结果、目标仍难看懂，或断线/重放导致重复结算，先修正规则或技术问题再扩大投放。

## 已确认决策与外部前提

1. 首版由 Unity 客户端裁决；画面采用俯视卡通海图、深海蓝与暖金灯光，以及 9:16 的信息布局。
2. Windows 直播客户端、WebGL 试玩与 Hub 视频／真实下载包属于同一项目。GitHub Pages 的 WebGL 不冒充正式直播玩法。
3. 正式 SDK 联调、玩法提审与真实主播试播需要外部账号资质和授权。如果该前提暂不可得，可完成可玩成品、模拟事件验收和公开试玩，但不能将其称为已完成抖音正式接入或完整平台验收。
