# 《灯塔救援队》正式直播存储故障停机规格

状态：2026-10-04，依据用户持续开发及直接完成授权实施。正式抖音 SDK 与玩法权限仍未取得，本规格只覆盖 SDK 无关的 Windows 直播消息链路。

## 目的

未来直播输入已被规则接受后，若完整检查点或追加日志写入失败，不能继续接收下一条并把未持久化状态报为已履约。主播需要立即看到可解释的停机原因；恢复要从最后可读取的持久状态开始，不能凭内存中未落盘的贡献继续结算。

## 设计

1. `RescueController.OnLiveReceipt` 在向适配器交回 `Applied` 回执之前执行持久化。任何持久化异常触发本局故障停机：不调用该条消息的 `HandleReceipt`，停止直播源，标记不可在本进程重连的 `Faulted` 状态，并阻断同帧及后续队列处理。
2. 优先从同房间的检查点与校验日志重建规则状态，重置视觉反馈基线。读回失败时保留当前画面但仍停机，不据此产生后续结算或 ACK。两种情况都不尝试在故障介质上再写一次“暂停”存档。
3. 故障停机期间，主播的开始、恢复、结束、重置和本地事件入口不能改变规则状态。重新启动客户端并修复存储后，按现有同房间恢复提示继续；本进程不自动重连。
4. 直播画面显示存储故障原因。普通断线仍遵守现有“先处理已入队消息、再暂停”的流程；正常事件顺序与 WebGL 模拟试玩不变。

## 验收

- 故障注入使第一条生效观众消息的日志追加失败，并预先排队第二条；`Update` 不抛异常，两个消息均无履约回执，第二条不进入规则，之后继续 `Update` 不推进倒计时。可读取检查点时观众数回退到最后持久值；主播画面说明存储失败。
- 检查点不可读取时仍停机，不崩溃、不发送回执、不继续结算。
- 正常直播消息、一般网络断线、恢复与模拟版既有测试继续通过；Unity EditMode 全量、Windows/WebGL 构建和公开包验收按发布流程执行。
- 尚无官方 SDK 时，不声称真实直播或官方 ACK 已验证。
